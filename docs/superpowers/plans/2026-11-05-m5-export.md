# Milestone 5: Export Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the editor, the owner exports a finished MP4 of the whole song or a chosen section, in Draft or Final quality, at 1080p or 1440p. While it runs they see:
- progress
- time remaining
- a Cancel button
- a browser notification when it's done

Then they download the file. **The first complete app.**

**Architecture:**
- **Export manager** (`src/lib/exports/`): runs one export at a time.
  1. Builds a job folder with `prepareJob` (M3).
  2. Runs `npx hyperframes render`, reading its `@hf-progress` lines.
  3. Re-encodes with FFmpeg, reading `-progress` lines.
  4. Saves the MP4 in `storage/exports/`.
- **Status:** each export's status is kept in memory and in a JSON file, so a restart can mark an interrupted export as failed.
- **Routes:** API routes start, read, cancel and download exports.
- **Editor:** an Export panel, a section strip on the song's waveform, and a background-image picker.

**Tech Stack:** Next.js 16.4.5 route handlers, Node `child_process.spawn`, FFmpeg 8, HyperFrames 0.9.10 CLI, React 19 + Tailwind, Vitest.

## What was checked before planning (2026-11-05)

- **`npx hyperframes render` writes JSON progress lines to stdout,** for example `@hf-progress {"code":"capture","done":105,"total":600,"pct":33}`. The codes and their `pct`:

  | code | pct |
  | --- | --- |
  | `compile` | 5 |
  | `extract_video` | 10 |
  | `process_audio` | 20 |
  | `start_browsers` | 25 |
  | `capture` (with `done`/`total` frames) | 25–70 |
  | `encode` | 75–90 |
  | `assemble` | 90–99 |

  A 20 s sample render at draft quality took 2 min 37 s overall, about 60 s of which was setup.
- **Resolution:** `--resolution` only offers whole multiples of the composition (1080p, 4K). There is no 720p or 1440p.
- **Sections:** sections are cut by the job builder (M3 ruling); `render --start/--end` is slow software rendering and must not be used.
- **Disk space:** free space is available through `fs.statfs` (84 GB free on this PC today).

## Global Constraints

- Export pipeline (spec §9):
  1. Job folder `storage/jobs/<exportId>/` (`prepareJob`, with the section and background).
  2. Render: `npx hyperframes render <jobDir> --variables-file <variables.json> --strict-variables --quality <draft|delivery> -o <jobDir>/raw.mp4`.
  3. Encode: FFmpeg H.264 CRF 20, AAC 320 kb/s, `+faststart` → `storage/exports/<Artist> - <Title> (<Template>).mp4`. Delete `raw.mp4` after success.
  4. On success, delete the job folder. On failure, keep it.
  5. Time estimate: percent done and elapsed time. Before progress starts, estimate ≈ 4× song length (Final).
  6. Cancel: kill the render process tree (`taskkill /T /F` on Windows), mark it cancelled, delete the job folder.
- **Only one export runs at a time.** A second request gets **409**, and the Export button is disabled while one runs.
- Error behaviour (spec §10):
  - Render fails → status "failed" with the last lines of the render log; the job folder is kept.
  - App restarted during an export → on start, unfinished jobs are marked failed, with the message "The app was restarted during this export."
  - Less than **5 GB** of free disk before export → warn before starting (the owner can still start).
  - Song over 10 minutes → show the expected export time before Export starts (always shown in the panel).
- Exact copy:
  - "The app was restarted during this export."
  - "Another export is running. Wait for it to finish or cancel it."
  - "Less than 5 GB of disk space is free. A long export may not fit."
  - "Couldn't read this image. Try JPG or PNG." (M3)
- **Never commit `storage/`, music, video or song-derived data.**
- **Templates are never modified by an export.** Everything happens in the job folder.
- Read the matching page in `node_modules/next/dist/docs/01-app/` before writing a route.
- Code the browser uses must not import `node:` modules.
- `npm run check` before every commit. Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Decisions this plan makes

1. **1440p:** render at 1080p, then scale to 2560×1440 (Lanczos) in our FFmpeg encode, because HyperFrames can't render 1440p. The panel labels it **"1440p (upscaled from 1080p)"**. It costs little extra time, unlike spec §4's estimated "roughly 1.8×" for native 1440p. True 1440p would need the template to draw at 2560×1440 itself; that is left for M7 if the owner wants it.
2. **Draft:** HyperFrames `--quality draft`, and our encode scales to **720p** with `-preset veryfast` (spec §9: "Draft lowers resolution to 720p"). Final: `--quality delivery`, then the encode at the chosen resolution with `-preset medium` (M3 ruling).
3. **Progress shown to the owner, 0–100:**
   - preparing 0–2
   - render = HyperFrames `pct` scaled into 2–90
   - our encode = FFmpeg `out_time` / duration, scaled into 90–100

   Time remaining:
   - **before capture has run 20 frames:** `estimateExportSeconds` minus elapsed time (never below 0)
   - **after that:** `elapsed / pct × (100 − pct)`
4. **Estimate:** `estimateExportSeconds(seconds, quality, resolution) = 60 + seconds × (final 4.0 | draft 3.0) × (1440p ? 1.1 : 1)`. That gives 4:12 Final ≈ 18 min (measured 17 min 19 s) and 60 min Final ≈ 4 h 1 min.
5. **Status lives in `storage/exports/<exportId>.json`,** rewritten at most once a second, plus in memory. `exportId` = `YYYYMMDD-HHMMSS-<4 random hex>`. Files that already exist get a ` (2)`, ` (3)`… suffix.
6. **Background image:**
   - `PUT /api/backgrounds` (raw body, like songs) converts the image to a 1920×1080 JPEG, cover-cropped and flattened onto black, saved as `storage/backgrounds/<sha256 of source>.jpg`. This also fixes M3's deferred "wide/transparent background" minor.
   - Choosing an image switches `showBackground` on.
   - The preview gets it through the media segment of its URL: `/preview/<t>/<songId>~<backgroundId>/…`.
7. **Notification:** browser `Notification`. Permission is asked when the owner ticks "Notify me when it's done" (needs a user gesture). The panel polls status every second and notifies once when it reaches `done` or `failed`.
8. **M4 deferred minors folded in because export depends on them:**
   - choosing a new song aborts the previous upload
   - `prepareSong` runs for the same song id are de-duplicated (one shared promise)
   - files over 1 GB are rejected in the browser before uploading

## Review Focus

1. **Cancel at each stage.** Cancelling during render (Chrome running) or during encode leaves no `chrome-headless-shell` / FFmpeg process, no half-written MP4 in `storage/exports/` and no job folder, and the status is "cancelled". Pinned by `cancel kills the running step's process tree and removes the job folder` (Task 2) and the manual cancel check (Task 7).
2. **App restarted mid-export.** The export shows as failed with the restart message, the Export button works again, and the job folder is kept for checking. Pinned by `loading marks unfinished exports as interrupted` (Task 3).
3. **Name collisions and unsafe names.** Exporting the same title twice gives `… (2).mp4`. A title with `\/:*?"<>|` gives a valid Windows file name. Pinned by `uniqueExportPath adds a number when the name is taken` (Task 2) and the existing `outputName` tests.
4. **A second export while one runs** (another tab, or a double click) → 409 with the exact message; the running export is untouched. Pinned by `starting while one runs is refused` (Task 3).
5. **Sections at the very start or end of a song, and a whole 60-minute song.** Durations are right, the estimate shows ≈ 4 h for 60 min, and a section handle can't pass the other one or the song's ends. Pinned by `clampSection keeps the handles in order and inside the song` (Task 5) and `estimate for 60 minutes Final is about 4 hours` (Task 1).

- Produces:
  ```ts
  // processes.ts
  export type Spawned = { pid: number | undefined; onLine(cb: (line: string) => void): void; done: Promise<number> }; // resolves with exit code
  export type Spawner = (cmd: string, args: string[]) => Spawned;
  export const spawnLines: Spawner; // real one: child_process.spawn, splits stdout+stderr on \r and \n; npx via shell on win32 (quote args with spaces)
  export function killTreeArgs(pid: number, platform: NodeJS.Platform): [string, string[]]; // win32 → ["taskkill", ["/PID", pid, "/T", "/F"]]; else ["kill", ["-TERM", `-${pid}`]]
  // encode.ts
  export function exportEncodeArgs(input: string, output: string, o: { quality: Quality; resolution: Resolution }): string[];
  // run-export.ts
  export type ExportRequest = { templateId: string; songId: string; values: TemplateValues; start?: number; end?: number;
    quality: Quality; resolution: Resolution; backgroundId?: string };
  export type ExportStage = "preparing" | "rendering" | "encoding";
  export type ExportUpdate = { stage: ExportStage; percent: number; framesCaptured: number };
  export function uniqueExportPath(dir: string, fileName: string): string; // "a.mp4" → "a (2).mp4" → "a (3).mp4"…
  export type RunExportOptions = { exportId: string; request: ExportRequest; projectRoot: string; spawn: Spawner;
    run: RunCommand; onUpdate(u: ExportUpdate): void; signal: AbortSignal };
  export async function runExport(o: RunExportOptions): Promise<{ file: string }>; // throws ExportFailed(lastLines) or ExportCancelled
  export class ExportFailed extends Error { constructor(message: string, readonly logTail: string[]) }
  export class ExportCancelled extends Error {}
  ```
- `exportEncodeArgs`:
  - `finalEncodeArgs` plus `-progress pipe:1 -nostats`.
  - Final 1440p adds `-vf scale=2560:1440:flags=lanczos`.
  - Draft adds `-vf scale=-2:720` and `-preset veryfast`.
- `runExport` steps:
  1. Job dir `storage/jobs/<exportId>/`.
  2. `prepareJob` with `section` (when start/end are given) and the background path `storage/backgrounds/<id>.jpg`.
  3. Render with the spawner. Parse `@hf-progress` and report `stage:"rendering"`; `framesCaptured` = the `done` of `capture` lines.
  4. Encode `raw.mp4` → `uniqueExportPath(storage/exports, outputName(values, templateName, start, end))`, writing to `<name>.part.mp4` and renaming it on success.
  5. Delete the job folder.

  Error handling:
  - A non-zero render or encode exit → `ExportFailed` with the last 20 output lines. The job folder is kept, and the `.part.mp4` is deleted.
  - When `signal` aborts:
    - kill the current process tree (`killTreeArgs` via `run`)
    - delete the job folder and any `.part.mp4`
    - throw `ExportCancelled`
